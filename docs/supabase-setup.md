# Supabase setup

The diary is stored in Supabase (Postgres + Auth). Sign-in is Google only.
Row-level security lets each user change only their own entries, and read only
their own and their friends'.

The schema lives in `supabase/migrations/`. These steps create the hosted
project, connect Google sign-in, and apply the schema. Everything here fits the
free tiers.

## 1. Create the Supabase project

1. At [supabase.com/dashboard](https://supabase.com/dashboard), create a new
   project. Pick the **East US** region (closest to NYU) and save the database
   password somewhere safe.
2. Note the **project ref**: the `abcdefghijklmnop` part of
   `https://abcdefghijklmnop.supabase.co`.

## 2. Create the Google OAuth client

In [Google Cloud Console](https://console.cloud.google.com/), create (or pick) a
project, then open **Google Auth Platform**:

1. **Branding**: app name (e.g. "sh-tboxd"), support email, developer email.
2. **Audience**: choose **External**. While the app is in **Testing**, only the
   Google accounts listed under *Test users* can sign in (up to 100), which suits
   a few friends. Add yourself and them there. Publishing to production instead
   needs no Google review, since the app only asks for name, email and picture.
3. **Data access**: keep the default scopes (`openid`, `email`, `profile`).
4. **Clients → Create client → Web application**:
   - *Authorized JavaScript origins*: `http://localhost:5173`
   - *Authorized redirect URIs*: `https://<project-ref>.supabase.co/auth/v1/callback`

   Copy the **client ID** and **client secret**.

When the app is deployed, add the Vercel URL to the authorized JavaScript
origins too (see [deploy.md](deploy.md)).

## 3. Turn on Google in Supabase

In the Supabase dashboard:

1. **Authentication → Sign In / Providers**:
   - **Google**: enable it and paste the client ID and secret.
   - **Email**: disable it, so Google is the only way in.
2. **Authentication → URL Configuration**:
   - *Site URL*: `http://localhost:5173` for now; change it to the Vercel URL
     once deployed.
   - *Redirect URLs*: add `http://localhost:5173/**` (and later the Vercel URL
     with `/**`).

## 4. Apply the schema

From the repo root:

```sh
npx supabase login
npx supabase link --project-ref <project-ref>   # asks for the database password
npm run db:push                                  # applies supabase/migrations/
```

In **Table Editor**, `entries` should now exist with RLS enabled.

## 5. Point the app at the project

Copy `.env.example` to `.env.local` and fill in the values from **Project
Settings → API Keys** (project URL and publishable key). `.env.local` is
gitignored. Then `npm run dev` and sign in with Google.

To put it online, continue with [deploy.md](deploy.md).

## Schema summary

`public.entries`, one row per logged visit:

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | Primary key; generated by the client |
| `user_id` | uuid | Defaults to the signed-in user; deleting the account deletes their entries |
| `building_id` | text | Building slug from `campusMap.ts` |
| `visited_on` | date | Required; 1900 to today (+1 day for timezones) |
| `floor` | text | At most 3 characters |
| `rating` | numeric(2,1) | 0 (unrated) or 0.5–5 in half steps |
| `notes` | text | At most 200 characters |
| `created_at`, `updated_at` | timestamptz | Set by the database; owner and `created_at` can't be changed |

Signed-out visitors have no access to the table. Signed-in users can insert,
update and delete only rows where `user_id` is their own, and select their own
rows and their friends'.

`public.profiles`, one row per user who has picked a username (a missing row is
what makes the app ask for one): `username` (unique, lowercase, 3–20 of
`a-z 0-9 _`) and `bio` (at most 160 characters). Readable by every signed-in
user; writable only by its owner.

`public.friendships`, one row per pair of users: `requester_id`,
`addressee_id`, and `status` (`pending` until the addressee accepts, then
`accepted`). Users can read rows they're in, plus their friends' accepted
friendships. Nobody writes the table directly; the app calls
`send_friend_request`, `respond_to_friend_request` and `remove_friend`.
`is_friend_of_me(other)` backs the friend-read policies.

`public.entry_likes`, one row per (entry, user who liked it). Users can like
entries they can read, remove their own likes, and read the likes on any entry
they can read (plus their own likes anywhere), so the author and their friends
see who liked an entry. `entry_like_summaries(entry_ids)` returns each
entry's like count and whether the caller liked it, for entries the caller can
read.
`supabase/tests/friendships_check.sql` checks these rules without changing
anything.

`public.delete_my_account()` deletes the caller's own account (and, by
cascade, their entries); it backs the app's **Delete account** menu item.

## Changing the schema later

```sh
npx supabase migration new <name>   # creates supabase/migrations/<timestamp>_<name>.sql
# write the SQL, then:
npm run db:push
npm run db:types                    # regenerates src/lib/database.types.ts
```

Optional: `npx supabase start` runs the whole stack locally in Docker. Put the
Google client ID and secret in `supabase/.env` (see `supabase/.env.example`) and
add `http://127.0.0.1:54321/auth/v1/callback` as a redirect URI on the Google
client to sign in against it.
